# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

"Khoi Pro" is a full-stack company system-of-record: an ASP.NET Core 10 Web API backend on PostgreSQL (EF Core, real migrations), paired with a React 18 + Tailwind CSS frontend. Core domain: Users/Roles/Permissions, Projects, Tasks, a hierarchical Space-based permission system (SharePoint/Confluence-style, see Architecture Notes), a secrets Vault, a Confluence-style Wiki, SharePoint-style file Libraries, HR onboarding, Finance/Invoicing, Timesheets, an Ideas board, a company Calendar, personal Reminders (with recurrence + snooze), Notifications, and dashboard/report endpoints.

Frontend is Vite + React 18 + plain JavaScript + Tailwind — **not** TypeScript, **not** Create React App/react-scripts (migrated off CRA), **not** React 19, no router library, no TanStack Query, no Zod. Confirm this before assuming otherwise; a differently-stacked skill or prompt template does not change what's actually here. Component files that contain JSX use the `.jsx` extension (required by Vite's default esbuild config — CRA didn't care); plain-JS files with no JSX (`services/`, `utils/`) stay `.js`.

## Solution Structure

The real solution is `KhoiProjectManagement.sln`. The backend follows Clean Architecture / Ports-and-Adapters across five projects, dependency direction `Domain ← Application ← Infrastructure ← Api`, with `Quartz` as a sibling of `Infrastructure` that also depends only on `Application` (the textbook direction — Application depends only on Domain, Infrastructure/Quartz implement/consume Application's ports, Api is the composition root):

- **KhoiProjectManagement.Domain/** — entity classes only, `PermissionLevel`/`SpaceType`/`VaultAuditAction` enums (kept inline in their owning entity file, e.g. `PermissionLevel` in `SpacePermission.cs`), and the `ISpaceScoped` marker interface. Zero package references — pure POCOs, no EF Core, no framework types. Organized by business capability, not by C# construct type: `Common/` (`BaseEntity` — the `int Id` base every single-PK entity inherits; the 6 composite-key join entities `ProjectTag`/`ProjectUser`/`RolePermission`/`TaskTag`/`UserRole`/`WikiPageTag` deliberately don't — plus `ISpaceScoped`, `Tag`, `EmailLog`, the few things genuinely shared across features), `Identity/`, `Spaces/`, `Projects/`, `Vault/`, `Wiki/`, `Library/`, `Hr/`, `Finance/`, `Timesheets/`, `Ideas/`, `Calendar/`, `Notifications/`, `Reminders/`, `Dashboard/`. Everything stays in the single flat `KhoiProjectManagement.Domain` namespace regardless of folder — the folders are physical-only, so moving a file never touches any consumer's `using` statements.
- **KhoiProjectManagement.Application/** — references only Domain. Organized by the *same* feature folders as Domain (`Identity/`, `Spaces/`, `Projects/`, `Vault/`, `Wiki/`, `Library/`, `Hr/`, `Finance/`, `Timesheets/`, `Ideas/`, `Calendar/`, `Notifications/`, `Reminders/`, `Dashboard/`, plus an Application-only `Reports/` with no Domain counterpart since reports are pure cross-entity read aggregation) — each holding that feature's business-logic service interface+implementation pair (one pair per domain area, e.g. `IWikiService`/`WikiService` in `Wiki/`, `IVaultService`/`VaultService` in `Vault/`), its DTOs (request/response shapes), and its `AbstractValidator<T>` classes, all three colocated per feature rather than split into project-wide `Services/`/`DTOs/`/`Validators/` folders. No MediatR/CQRS — this is still the plain service-pair pattern, just grouped differently on disk. `Common/` holds genuinely cross-feature pieces: `MentionParser` (consumed by both `Wiki/` and `Ideas/`) and `TeamMemberDto` (consumed by Identity/Projects/Reports alike). `Abstractions/` — the persistence and infrastructure ports Application depends on instead of any concrete implementation: `IRepository<T>` (generic — `Query()`/`FindAsync`/`Add`/`AddRange`/`Remove`/`RemoveRange`), `IUnitOfWork` (`SaveChangesAsync`/`BeginTransactionAsync`), `IAppTransaction`, `IEmailService`, `IVaultEncryptionService`, `ISpacePermissionResolver`, `IWikiPresenceTracker`, `ICurrentRequestContext` (all interfaces only — their implementations are Infrastructure; these were moved out of the per-feature folders since none of them has a paired Application-side class, unlike e.g. `IVaultService`/`VaultService`). `Authorization/` holds `SpaceReference`/`SpacePermissionRequirement`, since services construct these directly when calling `IAuthorizationService.AuthorizeAsync(...)`. Services never see a concrete `DbContext` — they inject `IRepository<TEntity>` per entity type touched (yes, sometimes several per constructor — the accepted cost of a generic-repository design over per-aggregate repositories) plus `IUnitOfWork` where they write. One deliberate escape hatch: `IWikiSearchRepository` (full-text search) — Postgres's `EF.Functions.ToTsVector`/`PlainToTsQuery` are provider-specific and unavailable without the concrete Npgsql package, so that one query lives behind its own narrow port implemented in Infrastructure, while permission-filtering/snippet-building around it stays in `WikiService` like any other business rule. Every file lives in the flat `KhoiProjectManagement.Application` namespace (the old `.Services`/`.DTOs`/`.Validators` sub-namespaces were collapsed when those folders stopped existing) — `Abstractions/` and `Authorization/` are the two folders whose namespace still matches their name, since those weren't fragmented.
- **KhoiProjectManagement.Infrastructure/** — references Domain and Application (to implement Application's ports). `Data/` (`ProjectManagementContext.cs` — EF Core `DbContext` + `OnModelCreating`, including the `HasMaxLength`/`IsRequired` Fluent API configuration for every entity, since Domain carries no persistence `DataAnnotations`; `ProjectManagementContextFactory.cs` — design-time factory for `dotnet ef`; `UtcDateTimeConverter.cs`; `DatabaseSeeder.cs`), `Migrations/` (kept as its own top-level folder, sibling to `Data/`, matching `dotnet ef`'s default `--output-dir` and not nested further — see Commands below), `Repositories/` (`Repository<T>`, `UnitOfWork`, `EfAppTransaction`, `WikiSearchRepository` — the concrete implementations of Application's ports, the only place `ProjectManagementContext` is directly visible outside its own definition), and `Services/` for infrastructure-flavored service implementations: `Email/EmailService.cs`+`Email/EmailTemplates.cs` (MailKit), `VaultEncryptionService` (ASP.NET Core Data Protection), `SpacePermissionResolver` (`IMemoryCache`-backed — implements Application's `ISpacePermissionResolver`, and legitimately injects `ProjectManagementContext` directly since it's Infrastructure's own concrete type), `WikiPresenceTracker` (in-memory SignalR presence/edit-lock state), `HttpCurrentRequestContext` (implements Application's `ICurrentRequestContext` via `IHttpContextAccessor` — the one place `IHttpContextAccessor` is allowed to be touched directly), and `Authorization/PermissionRequirement`/`PermissionAuthorizationHandler`/`PermissionPolicyProvider`/`SpacePermissionAuthorizationHandler` (implement ASP.NET Core's authorization framework interfaces; the handler implements against Application's moved `SpacePermissionRequirement`).
- **KhoiProjectManagement.Quartz/** — references only Application. Quartz.NET `IJob` implementations (`OverdueTaskCheckJob`, `ReminderDueCheckJob`) that constructor-inject `INotificationService`/`IReminderService` directly — Quartz's DI-integrated job factory creates a scope per execution automatically. Kept as its own project (not folded into Infrastructure or Api) so only it takes the `Quartz`/`Quartz.Extensions.Hosting` package references.
- **KhoiProjectManagementApi/** — the thin Presentation/composition-root layer, references Application, Infrastructure, and Quartz: `Controllers/` (one per domain area), `Hubs/WikiHub.cs` (SignalR — real-time wiki presence/edit-lock, a real-time entry point exactly like a Controller, not Infrastructure), `Middleware/ErrorHandlingMiddleware.cs`, `Extensions/ServiceCollectionExtensions.cs` (DI/auth/CORS wiring, including the open-generic `IRepository<>`→`Repository<>` registration), `Program.cs` (also registers the Quartz scheduler + triggers — see Background work below).
- **KhoiProjectManagementApp/** — despite having its own `.csproj`/`Program.cs`, that ASP.NET stub is an empty, unused "Hello World" scaffold. The actual frontend is the React app living in the same folder (`src/`, `package.json`, `index.html` at the project root, `vite.config.js`, `public/` for static assets only) — treat this directory as a Vite project, not a .NET project. It has its own `.sln` as well, which can be ignored.

**KhoiManagementApp/** at the repo root is a separate, unreferenced default ASP.NET Core MVC template (default `HomeController`, scaffolded Views, bundled Bootstrap/jQuery). It is not part of `KhoiProjectManagement.sln` and nothing else depends on it — leftover scaffolding, not active code.

Package versions are centrally managed via `Directory.Packages.props` (root) — add new packages there, reference by name only (no `Version=`) in each `.csproj`. `Directory.Build.props` sets `TargetFramework`/`Nullable`/`ImplicitUsings` for every project. `CentralPackageTransitivePinningEnabled` is on — if a new transitive EF Core (or similar) dependency shows up as a version-conflict build warning, add an explicit `<PackageVersion>` pin for it rather than ignoring the warning.

## Commands

Backend (run from `KhoiProjectManagementApi/`, or `dotnet build`/`dotnet run --project KhoiProjectManagementApi` from the repo root):
- `docker compose up -d` — starts local Postgres (see root `docker-compose.yml`).
- `dotnet build` — build the whole solution.
- `dotnet run` — run the API; on startup it calls `Database.MigrateAsync()` then `DatabaseSeeder.SeedAsync()`. Swagger UI is available at `/swagger` in both Development and Production (see `Program.cs`).
- `dotnet ef migrations add <Name> --project ..\KhoiProjectManagement.Infrastructure --startup-project .` (run from `KhoiProjectManagementApi/`) — the `DbContext` and its design-time factory live in the Infrastructure project now, not the startup project, so both `--project` and `--startup-project` must be passed explicitly.
- Connection string, JWT secret, and SMTP credentials live in `KhoiProjectManagementApi/appsettings.json`, which is committed to git with real-looking credentials — treat as sensitive, do not add more secrets here, and flag this to the user rather than propagating the pattern.

Frontend (run from `KhoiProjectManagementApp/`):
- `npm install`
- `npm run dev` (or `npm start`, kept as an alias) — Vite dev server on port 3000 (`vite.config.js`). The API's `App:FrontendBaseUrl` (used to build password-reset links) and `Cors:AllowedOrigins` in `appsettings.json` both assume port 3000 — if you change the dev server port, update both.
- `npm run build` — production build (Vite, output to `build/` — `vite.config.js` pins `outDir` there instead of Vite's `dist` default so nothing downstream needed to change)
- `npm run preview` — serve the production build locally
- Env vars use the `VITE_` prefix (`import.meta.env.VITE_*`), not CRA's `REACT_APP_`; only `VITE_API_URL` is actually consumed in code (`ApiService.js`, `wikiHub.js`).

Backend tests live under `tests/` (all wired into `KhoiProjectManagement.sln`): `KhoiProjectManagement.UnitTests` (xUnit + NSubstitute/MockQueryable mocking `IRepository<T>`/`IUnitOfWork`, plus an InMemory-provider `ProjectManagementContext` for `SpacePermissionResolverTests` specifically), `KhoiProjectManagement.IntegrationTests` (boots the real Api in-process via `WebApplicationFactory<Program>` against a throwaway Testcontainers Postgres instance), `KhoiProjectManagement.FunctionalTests` (reuses IntegrationTests' fixtures), and `KhoiProjectManagement.ArchitectureTests` (NetArchTest.Rules — enforces the layer-dependency rules this section describes at build time: Domain/Application/Infrastructure/Quartz never depend on a layer above them, controllers only in Api, `DbContext` subclasses only in `Infrastructure.Data`, `*Repository` classes only in `Infrastructure.Repositories`). No lint config on the frontend (CRA's `eslintConfig` was removed along with `react-scripts`), but `KhoiProjectManagementApp/` does have Vitest (`npm test`/`test:run`/`test:coverage`) with `*.test.js` files co-located under `src/utils/`.

## Architecture Notes

- **Auth**: JWT bearer tokens (`Microsoft.AspNetCore.Authentication.JwtBearer`), issued/validated per `Jwt:Issuer`/`Jwt:Audience`/`Jwt:SecretKey` in config; passwords hashed with BCrypt; refresh tokens are opaque, hashed, and stored (`RefreshToken` entity) with rotation on use. Controllers are `[Authorize]` by default. Forgot/reset password (`POST /api/auth/forgot-password`, `POST /api/auth/reset-password`) follows the same opaque-hashed-token pattern via `PasswordResetToken` (1-hour expiry); `forgot-password` always returns `204` regardless of whether the email exists (including when the reset email itself fails to send — see Email below), and a successful reset revokes all of that user's active refresh tokens.
- **Permissions — two mechanisms, one pipeline**: flat, policy-based checks for fixed CRUD resources (`[Authorize(Policy = "projects.delete")]`-style, synthesized on the fly by `PermissionPolicyProvider`) for Users/Projects/Tasks/etc., plus resource-based checks (`SpacePermissionAuthorizationHandler`) for anything that lives in the hierarchical `Space` tree (Vault categories, Wiki spaces, Library folders) — a Space's effective permission level is resolved by walking `ParentSpaceId` upward via `SpacePermissionResolver` until an explicit grant or an inheritance boundary is hit. Both handler types are registered together in one ASP.NET Core authorization pipeline.
- **Layering**: Controllers are thin — they delegate to an `IXxxService`/`XxxService` pair (Application layer) registered in `ServiceCollectionExtensions.AddApplicationServices`, which inject `IRepository<TEntity>`/`IUnitOfWork` (never a concrete `DbContext`) — no MediatR/CQRS, but a generic repository + unit-of-work does sit between Application and EF Core (see Solution Structure above for the exact port/adapter split and the one full-text-search exception).
- **Mapping**: no AutoMapper (removed — it was a referenced dependency with zero actual usage) — mapping between entities and DTOs is done by hand in each service. Don't assume a project-wide mapping convention exists.
- **Validation**: FluentValidation *is* wired up (unlike AutoMapper) — every `AbstractValidator<T>` anywhere in the Application assembly (one `*Validators.cs` file per feature folder, e.g. `Application/Vault/VaultValidators.cs`, not a project-wide `Validators/` folder) is picked up by `AddValidatorsFromAssemblyContaining<LoginRequestDtoValidator>()` and run automatically by `ValidationActionFilter` (`Api/Filters/`, registered globally on `AddControllers`) against every controller action argument before the action executes, including `List<TDto>` arguments (each element validated individually, e.g. `SetPermissions(List<SetSpacePermissionDto>)`). A failure short-circuits with `400 { errors: { "Field": ["message"] } }` — no per-controller wiring needed once a DTO has a validator. Not every DTO has one; add an `AbstractValidator<T>` for a new input DTO in that feature's `*Validators.cs` file and it's picked up with zero other changes (assembly-scan based, not path based). `FluentValidation.ValidationException` is also caught in `ErrorHandlingMiddleware` as a defense-in-depth fallback for any service that calls `ValidateAndThrowAsync` directly instead of going through a controller argument.
- **EF Core relationships**: composite keys for the `ProjectUser`/`ProjectTag`/`TaskTag` join entities are configured in `ProjectManagementContext.OnModelCreating`, along with `Restrict`/`SetNull` delete behaviors for `Project.Creator`, `ProjectTask.AssignedTo`, and `Attachment.UploadedByUser`. Seed data (users, tags) is also defined there via `HasData`, separate from the runtime `DatabaseSeeder.SeedAsync`.
- **Background work**: Quartz.NET (`KhoiProjectManagement.Quartz/`), registered in `Program.cs` via `AddQuartz`/`AddQuartzHostedService` — **do not add both an eager `AddQuartzHostedService` call AND rely on `AddQuartz` alone**; the combination is correct and required here, but a recurring trigger's `.WithSimpleSchedule(...)` start time must never be left at the fluent-builder default of "now" (or a short fixed offset) — that time is computed eagerly at DI-registration time, well before the scheduler actually starts (this app's migration/seed step alone can take several seconds), and a stale start time races Quartz's misfire-recovery pass into firing the trigger twice. Both recurring triggers are deliberately started `DateBuilder.FutureDate(1, IntervalUnit.Hour)` out; the "check immediately on boot" behavior (matching the old `BackgroundService` loop this replaced) is reproduced explicitly and exactly once via `scheduler.TriggerJob(jobKey)` in `Program.cs`, called after seeding completes and before `app.RunAsync()`.
- **Email**: `EmailService`/`IEmailService` send via MailKit/MimeKit using the `Email:*` SMTP settings in config; sends are recorded via the `EmailLog` entity and logged via `ILogger<EmailService>` (success at Information, failure at Error). Every `Send*EmailAsync` method builds a short inner-content fragment and wraps it with `EmailTemplates.Wrap(headline, bodyHtml, ctaText?, ctaUrl?)` (`Infrastructure/Services/Email/EmailTemplates.cs`) for a consistent branded HTML shell (header bar in the app's brand color, optional CTA button with a plain-text URL fallback, footer) — add a new email by writing its inner fragment and calling `Wrap`, not by hand-rolling another full HTML document. `AuthService.RequestPasswordResetAsync` deliberately swallows (logs, doesn't rethrow) a failed `SendPasswordResetEmailAsync` call — letting it propagate would turn a `500` vs `204` into an email-enumeration side channel.
- **Logging**: Serilog, configured entirely from the `"Serilog"` section in `appsettings.json` (Console + rolling-daily File sinks under `Logs/`) — `Program.cs` uses the standard bootstrap-logger-then-`UseSerilog((ctx,svc,cfg)=>...)` pattern and wraps startup in try/catch/finally so failures are never lost. `app.UseSerilogRequestLogging()` logs every HTTP request. `ILogger<T>` is injected at the points worth a signal, not sprinkled everywhere: `AuthService` (login success/failure, refresh-token rejection, logout-all), `EmailService` (send success/failure), `VaultAuditService` (mirrors every vault audit event to Serilog — `SecretRevealed`/`AccessDenied` at Warning, the rest at Information — `VaultAuditLog` in the DB stays the per-entry queryable source of truth), `SpacePermissionAuthorizationHandler` (denied Space-scoped access, at Warning — otherwise invisible since no `[Authorize(Policy=...)]` attribute ever fires for these), and `PermissionAuthorizationHandler` (denied flat-permission checks, at Debug — high-volume/low-signal individually, unlike the Space-scoped case).
- **CORS**: must allow the React dev origin explicitly — the allowed-origins list is duplicated (with different port lists) between `appsettings.json`'s `Cors:AllowedOrigins` and the hardcoded fallback array in `ServiceCollectionExtensions.AddApplicationServices`; update both if changing ports.
- **Frontend structure**: `src/components/` is organized by concern, but **`Auth/AuthGuard.jsx`, `Auth/LoginForm.jsx`, `Layout/*`, and `Pages/*` are dead code** — never imported from anywhere. The actually-live login screen, header/nav shell, and tab-routing "AuthGuard" logic are all defined inline inside `App.jsx` (a `LoginForm` const, the main `ProjectManagementSystem` const, and an `AuthGuard` const at the bottom) — grep for a component's usage before assuming the file under `Layout/`/`Pages/`/`Auth/` is what actually renders. `Auth/ForgotPasswordForm.jsx` and `Auth/ResetPasswordForm.jsx` are the exception — genuinely live, imported and used by `App.jsx`'s `AuthGuard`. `Models/` (modal dialogs) and `Common/` (badges, spinners, error display) also contain a mix of live and orphaned files; check usage rather than assuming. `contexts/AuthContext.js` holds auth state; `services/ApiService.js` centralizes API calls and JWT header injection. Since there's no router, `AuthGuard` detects the emailed password-reset link (`window.location.pathname === '/reset-password'` + a `token` query param) the same manual way Wiki/Library share links are detected elsewhere in `App.jsx`.
